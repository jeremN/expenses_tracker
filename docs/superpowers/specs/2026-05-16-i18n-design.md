# i18n (EN/FR) — Design

**Status:** approved during brainstorm 2026-05-16
**Scope:** Tier 3 polish, feature 2 of 3 (CSV export → **i18n** → multi-currency)
**Implementation target:** single PR, per-area commits

## Goal

Make the entire UI available in English and French. Solo user; language is a personal display preference. Establish the locale-aware `Intl` formatting layer that multi-currency (feature 3) will extend.

## Non-goals

- **Error / validation message translation** — deferred to a follow-up. Server-side per-request locale + Zod locale-aware error map is the costliest part and not needed to unblock multi-currency. Server errors keep returning English for now.
- **User-entered data translation** — category names, descriptions, notes stay exactly as the user typed them, in both languages. Standard i18n practice; avoids data corruption and translation-API cost.
- **Currency symbol / `style:'currency'`** — owned by feature 3 (multi-currency). This feature formats the *number* per locale only.
- **Languages beyond EN/FR.**
- **Lazy-loading dictionaries** — both are small; always loaded.
- **Pluralization engine** — the app's few count-bearing strings are phrased to avoid plural grammar.

## Decisions (locked during brainstorm)

| Decision | Choice |
|---|---|
| Library | Custom React context + flat JSON dicts, zero dependencies |
| Persistence | `localStorage` (`locale` key) |
| SSR first paint | `Accept-Language` header → server renders EN or FR |
| Post-mount | `localStorage` overrides the header-derived locale |
| Scope | UI chrome + `Intl` number/date formatting |
| FR source | Anchor on v1's vetted vocabulary, translate the rest, user reviews `fr.json` |

## Architecture

New module: `apps/web/src/i18n/`

- `en.json`, `fr.json` — flat dictionaries. Dotted keys (`nav.dashboard`, `dashboard.subtitle`, `common.save`). Not nested.
- `index.ts` exports:
  - `type Locale = 'en' | 'fr'`
  - `LocaleProvider` — React context holding `{ locale: Locale; setLocale: (l: Locale) => void }`
  - `useTranslation()` → `{ t, locale }`
  - `parseAcceptLanguage(header: string | null): Locale`
- `apps/web/src/lib/format.ts` exports `useFormat()` → `{ formatMoney, formatDate }`

### `t(key, vars?)` semantics

- Lookup order (fallback chain): active-locale dict → `en` dict → the key string itself
- Missing keys never throw; they render the key (visible, debuggable, non-fatal)
- Interpolation: replace every `{name}` token with `String(vars[name])`. No pluralization.

```ts
function t(key: string, vars?: Record<string, string | number>): string {
  let s = activeDict[key] ?? en[key] ?? key
  if (vars) {
    for (const [k, v] of Object.entries(vars)) {
      s = s.split(`{${k}}`).join(String(v))
    }
  }
  return s
}
```

### `parseAcceptLanguage`

Tiny heuristic — not a full RFC-4647 matcher (only 2 locales):

- Take the first language subtag (split on `,`, then `;`, then trim)
- If it starts with `fr` (case-insensitive) → `'fr'`
- Else → `'en'` (covers unsupported languages like `de-DE` → default EN, and empty/null → EN)

### SSR locale flow

1. Root route loader reads the request `Accept-Language` header via TanStack Start's request access, runs `parseAcceptLanguage` → `serverLocale`
2. Root loader returns `{ locale: serverLocale }` (serialized to the client by TanStack Start)
3. Server renders the tree wrapped in `<LocaleProvider initial={serverLocale}>`; sets `<html lang={serverLocale}>`
4. Client hydrates using the **same** loader-provided locale → no hydration mismatch
5. Post-mount `useEffect`: read `localStorage.getItem('locale')`; if present, valid, and different from current, `setLocale(stored)`
6. Language selector on `/settings`: `setLocale(next)` + `localStorage.setItem('locale', next)`

The only visible flash is the narrow case where the stored preference differs from the browser's `Accept-Language` — same trade-off profile as the existing theme toggle's inline-script approach.

## Dictionary structure & key strategy

Flat keys with one namespace prefix per page/concern:

`nav.`, `common.`, `dashboard.`, `transactions.`, `recurring.`, `investments.`, `import.`, `categories.`, `stats.`, `settings.`

`common.` holds cross-page reused strings (Save, Cancel, Delete, Edit, Add, etc.).

Example:

```json
{
  "nav.dashboard": "Dashboard",
  "nav.settings": "Settings",
  "dashboard.title": "Dashboard",
  "dashboard.subtitle": "Your financial overview at a glance.",
  "common.save": "Save",
  "common.cancel": "Cancel",
  "import.result": "Successfully imported {imported} of {total} transactions from {filename}.",
  "settings.language.title": "Language"
}
```

### FR vocabulary anchoring

v1's `expenses-tracker/src/locales/fr/translation.js` (76 vetted entries) is the terminology anchor:
`Expense→Dépense`, `Income→Revenu`, `Amount→Montant`, `Category→Catégorie`, `Date→Date`, `Save→Sauvegarder`, `Cancel→Annuler`, `Delete→Effacer`, `Edit→Éditer`, all 12 month names. New v2-only strings are translated in the same register. User reviews the final `fr.json`.

### Extraction discipline

- Every user-facing literal in `apps/web/src/routes/` and `apps/web/src/components/` is replaced with `t('namespace.key')`
- User-entered data is **never** wrapped
- `routeTree.gen.ts`, test files, and config are untouched

## Intl formatting

`apps/web/src/lib/format.ts`. The existing `formatCents` in `lib/utils.ts` is **removed** (migrated here, pre-launch, no back-compat shim). `cn` and `parseToCents` stay in `utils.ts`.

Locale tag mapping: `en → 'en-US'`, `fr → 'fr-FR'`.

```ts
function useFormat() {
  const { locale } = useTranslation()
  const tag = locale === 'fr' ? 'fr-FR' : 'en-US'
  return {
    formatMoney: (cents: number) =>
      new Intl.NumberFormat(tag, { minimumFractionDigits: 2, maximumFractionDigits: 2 })
        .format(cents / 100),
    formatDate: (isoDate: string) => {
      // Stored as 'YYYY-MM-DD'. Parse as a local calendar date — NOT
      // `new Date(isoDate)`, which interprets it as UTC midnight and shifts
      // the day in negative-offset timezones.
      const [y, m, d] = isoDate.split('-').map(Number)
      return new Intl.DateTimeFormat(tag).format(new Date(y, m - 1, d))
    },
  }
}
```

- **No currency symbol / `style:'currency'`** — this feature formats the number only (`1,234.56` en vs `1 234,56` fr). Multi-currency (feature 3) wraps `formatMoney` with `style:'currency'` + a `currency` argument. This is the deliberate seam from the original Tier-3 decomposition: multi-currency becomes a wrapping change, not a second pass over every call site.
- **Date format:** locale default short format (`5/16/2026` en, `16/05/2026` fr). Long-form is a one-line option change if wanted later.

### Migration

Every component calling `formatCents(...)` switches to `const { formatMoney } = useFormat()`. Date displays similarly use `formatDate`. This is the broad-but-mechanical part: summary cards, transaction table, charts, recurring list, investments, stats.

## Settings UI

`/settings` (from feature 1) gains a second card, "Language", placed **above** the existing "Export data" card (language affects how the whole page reads, so it leads):

- shadcn `Select` with two options: `English`, `Français`
- `onValueChange` → `setLocale(value)` + `localStorage.setItem('locale', value)`
- The card's own title/description use `t()` (`settings.language.title`, `settings.language.description`)

## Testing

| Test file | Cases |
|---|---|
| `apps/web/src/i18n/index.test.ts` | (1) `t()` returns FR when locale=fr, EN when en; (2) fallback FR-missing→EN, all-missing→key; (3) interpolation substitutes every `{var}`; (4) `parseAcceptLanguage`: `fr-FR,fr;q=0.9,en`→fr, `en-US,en`→en, `''`→en, `null`→en, `de-DE`→en; (5) **key-parity**: `Object.keys(en).sort()` deep-equals `Object.keys(fr).sort()` |
| `apps/web/src/lib/format.test.ts` | (1) `formatMoney(123456)` → `'1,234.56'` (en-US) / `'1 234,56'` (fr-FR, asserting the U+202F narrow no-break space exactly); (2) `formatMoney(-50000)` sign handling; (3) `formatDate('2026-05-16')` → `'5/16/2026'` (en) / `'16/05/2026'` (fr); (4) `formatDate` no off-by-one (e.g. `'2026-01-01'` stays Jan 1, not Dec 31) |

The key-parity test is the load-bearing guard: it fails CI the moment `en.json` and `fr.json` diverge in key set (missing translation, or a key added to one file only).

SSR/hydration is verified by manual QA, not unit-tested:
- `curl -H 'Accept-Language: fr-FR' /` → French SSR HTML
- `curl -H 'Accept-Language: en-US' /` → English SSR HTML
- In browser: switch via Settings, reload, confirm `localStorage` persisted and overrides header

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Hydration mismatch | Hydrate from serialized root-loader locale; defer `localStorage` override to post-mount `useEffect` |
| Missed strings during extraction | Key-parity test + per-area commits + best-effort grep sweep for bare JSX string literals (documented non-exhaustive); residual risk is graceful (English fallback, not a crash) |
| FR narrow-NBSP (U+202F) thousands sep | Tests assert the exact codepoint, with a comment explaining it's not a regular space |
| Bundle size | ~10-15 KB raw for both dicts; acceptable, no lazy-loading complexity |
| `route-error.tsx` rendering before context | `t()` fallback chain degrades to English/key; acceptable on a catastrophic error path |

## Effort estimate

i18n core is small (~120 LOC). The extraction touches ~28 files. ~8-10 tasks, single PR with per-area commits. Multi-currency (feature 3) then builds purely on `useFormat`.
